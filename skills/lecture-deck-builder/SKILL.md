# Lecture deck builder: art board first, reveal.js second

Two phases. Never skip ahead: the board is where the instructor iterates; export only when they say they are happy.

1. **Board phase**: build every slide as a 1280×720 artboard on a Design-type art board and revise there. Keep the converter (`board-to-reveal`, in the slidewright repo) able to export every kind of slide on the board (section 3, rule 11), and save the code behind every computed number (section 3, rule 10).
2. **Export phase**: Claude runs `board-to-reveal` on the latest board, checks the result and delivers ONE self-contained reveal.js .html file plus ONE companion Jupyter notebook (.ipynb) with the code behind the lecture's numbers and graphs (section 4). The instructor does not run anything locally.

Sections 1–5 are rules for every deck. Section 6 is a record of past lectures: reference only, never defaults.

## 1. Notation (course-wide; apply everywhere, never substitute textbook defaults)

| Thing | Write | Never write |
|---|---|---|
| Linear output / logits | **ŷ** (matrix **Ŷ**) | z |
| Predicted probability / activation output | **p̂** (matrix **P̂**) | ŷ for probabilities |
| True label / true distribution | **p** (matrix **P**) | y |
| Activation Jacobian | **∂P̂/∂Ŷ** (per entry ∂p̂ᵢ/∂ŷⱼ) | J |
| Upstream gradient | **∂L/∂P̂** (per entry ∂L/∂p̂ᵢ) | g |
| Gradient to logits | **∂L/∂Ŷ** | — |
| Weights, inputs | **W**, **X** (Ŷ = XWᵀ) | — |
| Shapes | examples × classes / neurons / features (e, n, f) | — |

General rules:
- Write derivatives out in full (∂L/∂P̂ · ∂P̂/∂Ŷ); don't invent single-letter shorthands. A named intermediate for a computed quantity is fine if defined on the slide.
- Keep signs explicit (e.g. off-diagonal Jacobian terms carry their minus).
- Compare scales in scientific notation (10², 10⁶, 2.5 × 10⁹).
- Elementwise products of matrices are ⊙ (Hadamard), never ×; × is for scalars (one unit's values).
- If a new topic needs a symbol not listed here, ask the instructor once and then use it consistently.

### Math typesetting
- **On the board** (no math library allowed there): Unicode math in IBM Plex Mono with `<sub>`/`<sup>` and combining characters (p̂ = `p̂`, ŷ = `ŷ`, P̂, Ŷ). Inline fractions like `∂L/∂p̂ᵢ`.
- **In the reveal export**, KaTeX for anything needing 2D layout (stacked fractions, matrices, big brackets), written as `\( … \)` / `\[ … \]`. Hats: `\hat{p}_i`, `\hat{y}_j`, `\hat{P}`, `\hat{Y}`, never `\widehat{p_i}` (it stretches the hat over the subscript). The converter inlines KaTeX automatically when any slide contains these delimiters.
- Board slides go into the export as-is, so equations look identical between board and deck.

## 2. Visual system

- Fonts: IBM Plex Sans (text), IBM Plex Mono (math, labels, code). Google Fonts on the board; embedded woff2 in the export.
- Ground `#FBFBFA`; ink `#16181D`; muted `#4E5360`; captions `#5A5F6B`; rules `#DADDE2`.
- Blue `#2557D6` (tint `#DCE5FA`, dark `#1B3F9E`): the highlighted item, positive values, diagonal / own-term pieces.
- Orange `#C2510F` (tint `#FBE3D2`, dark `#8A3A0A`): negative values, off-diagonal / coupling pieces. Backward-pass arrows `#C2410C`.
- Colour must carry meaning: when a lecture assigns a meaning (a path, a dimension), keep it identical on every slide and in every label, equation term and legend that refers to it.
- Dashed outline (`2px dashed #8A3A0A`): a term that is shared / computed once.
- Dark panels `#16181D` for key results; code `#1E2127` with keyword `#C792EA`, function `#82AAFF`, comment `#8A93A3`, number `#F78C6C`, self `#F07178`.
- Slide anatomy: title 48px/600, subtitle 21px muted, body, then a takeaway line above a 1px rule with **one bolded phrase**.
- **Discussion badge**: every slide where students are expected to answer (question slides, polls, "guess the year", "shout out the missing word", "finish the sentence") gets the instructor's question-mark badge in the top-right corner: `<div role="img" aria-label="Discussion question" style="position: absolute; left: 1136px; top: 40px; width: 72px; height: 72px; box-sizing: border-box; border-radius: 50%; background: #16181D; color: #FBFBFA; display: flex; align-items: center; justify-content: center; font-size: 50px; line-height: 1; font-weight: 600">?</div>` (left 1144px on slides with a 64px margin). Narrow the title and subtitle (1048px at a 72px margin, 1064px at 64px) so they clear it. No badge on slides where the instructor only explains.
- **No slide numbers or "STEP n" labels.** No emoji, no gradients.
- **Copyright line and PDF button are added by the export** (section 4), never drawn on the board. Each one moves to a free spot on its slide when the deck loads, so the board needs no reserved space.
- Matrices and heatmaps: label rows and columns, put each cell's formula in the cell even if tiny, add a legend (positive / negative / exactly 0).

### Diagrams
- Values are arrow labels; only operations (· Wᵀ, σ(·), ⊙, ×, Σ, Linear, Norm, softmax) are boxes or nodes. Be consistent: X always enters a `· Wᵀ` box.
- Forward lines solid, gradients dashed; derivatives connect vertically to the function they come from (function on top, ↓ ∂/∂ŷ arrow, derivative below).
- When a slide shows an expanded unit-level view and a collapsed layer view, make the collapsed block the same width and align each block under the part it stands for.
- Show mechanisms, not mystery boxes: e.g. a router is drawn as its linear projection (one Σ per output) followed by a softmax.
- Arrow marker ids `dc-arrow-head-filled-N` must be unique within a file.

## 3. Phase 1: board

1. Create from the **Design** type (title = the lecture topic). One artboard per slide, 1280×720, in one row (x step 1360) in teaching order; artboard `title` = slide name, no numbers. One `title1` note above the row.
2. Diagrams (forward/backward passes, flows) are separate placed elements per the type's diagrams reference, so the instructor can drag and retype pieces.
3. Simple example images (e.g. dataset samples) can be generated as pixel grids in `renderVals()` so they need no upload.
4. Before every edit, re-read any artboard the instructor may have touched (the view context's `edits` count going up means something changed); their hand edits win, including deletions. Change only what was asked.
5. When the instructor attaches reference slides (screenshots), match their structure and content, restyled into this visual system.
6. Choose a running example that fits the new lecture's topic; ask if unsure. Don't reuse a past lecture's example unless asked.
7. **Removing or hiding a slide** ("remove", "cut", "we won't have time for", "hide"): never delete the board. Hide it: make sure `canvas.json` has `pages` `[{"id":"deck","name":"Deck"},{"id":"hidden","name":"Hidden"}]`, give the board `"page":"hidden"` and `x: 0` on that page, keep it in its place in `order` (so it returns to the same spot when un-hidden), and re-space the visible deck row. The export keeps every hidden board in the file, in order, as `<section data-visibility="hidden">` with a `(HIDDEN …)` comment, so reveal.js drops it at load: not shown, not counted, not in the PDF. To bring one back, move it to the Deck page and re-export. Delete a board only when the instructor explicitly asks for it to be deleted.
8. **Question slides** before a reveal ("ask the students why…"): same visuals as the reveal slide minus the answer, subtitle "Talk it over with a neighbour before we move on", the question in a dark panel, and the discussion badge (section 2). When the question and its answer belong on one slide ("What is AI?"), show the question first and bring the answer in with `data-build-step` (rule 9), the takeaway line included, so the slide does not give the answer away before students talk.
9. **Click-through slides** (things that appear or change on each click). Prefer patterns the converter already supports (`board-to-reveal/COVERAGE.md` in the slidewright repo). Every click-through slide must be previewable on the board: the instructor clicks Next/Reset (or uses the Build "step" control) and sees each click as students will.
   - Keep the step in `this.state.step` (fall back to `this.props.step ?? …`) and declare it in `data-props` as `"step":{"editor":"int","default":N,"min":0,"max":N,"section":"Build"}`. **`max` is how the converter knows the slide has N steps.** Next/Reset are ordinary `<button>`s wired to `setState`; the export removes them. Set `"is_interactive": true` on the board and add "(click Next)" to its board title.
   - **Default: build-preview items.** When clicks only bring items in, take them out, dim or highlight them, mark each item with `data-build-step="k"` (k from 1) and optionally `data-build-effect` (`fade-up`, `fade-down`, `fade-left`, `fade-right`, `current-visible`, `fade-in-then-out`, `fade-in-then-semi-out`, `fade-out`, `semi-fade-out`, `grow`, `shrink`, `highlight-red`, `highlight-green`, `highlight-blue`, `strike`; none = fade in). Put `--step: {{step}}` in the slide root's style and paste `board-to-reveal/build-preview.css` verbatim into the slide's `<helmet><style>`. Use `default` = `max` so the board's overview shows the finished slide. Highlight items take their resting colour from `--base: #…`, not `color`; don't put an inline `transform` on effect items (wrap them instead). The export turns each item into one reveal fragment with the same effect: no full-slide copies, a small file, and the instructor can change effects and order in Slidewright. The step must change nothing else on such a slide (the converter stops if it does).
   - Elements that should glide between steps (e.g. pixels moving to new spots) get absolute `left:…px; top:…px` plus an inline `transition: left …, top …`; `renderVals()` moves them with the step. When a step changes only those positions, the export animates them; any other change (text swaps, `<sc-if>` content) becomes a full fade-in layer, so use that only when items really change in place.
   - SVG `<circle data-build-dot="name" data-track="x1,y1;x2,y2;…" cx="x1" cy="y1">` is a marker that moves along a plot (one pair per step, viewBox coordinates, drawn at its first position); the board shows it at step 1 and the stepping happens only in the export.
   - Time-driven motion (a loop, or a short flight started by Next): `componentDidMount()` starts a timer that calls `setState` with a clock value, `renderVals()` turns it into attribute values (`transform`, `opacity`, colours) or an element's whole text, and the reduced-motion branch sets the resting state. Keep `<sc-for>`/`<sc-if>` output fixed while it plays. In `sc-if`/`sc-for` attributes, use a precomputed boolean (`{{s2}}`), never a comparison with `>` in it.
10. **Keep the code behind every number.** Any number, table, plot curve, heatmap or image on a slide that comes from code (an experiment, a training run, a calculation, a plotted function) is computed by a saved script, never a throwaway one-liner. Keep these scripts in one folder (e.g. `<scratchpad>/lecture-code/`), one per slide or experiment, named after the slide, with seeds and constants fixed, and save their results (JSON) next to them. Load data the way the notebook will (e.g. from the dataset by index, not from a reordered or rounded copy), so the notebook reproduces the slide exactly. Code that only draws the slide (SVG paths, pixel coordinates, encoded images) does not count; the computation does. Values a slide computes in its own `renderVals()` count too. Note illustrative numbers, paper figures and the instructor's own numbers as such when they go on a slide. This folder is what the companion notebook is built from at export (section 4, step 5).
11. **Keep the converter in sync with the board, and with Slidewright.** The converter lives in the **slidewright** repo (`JesseTNRoberts/slidewright`, folder `board-to-reveal/`), next to Slidewright, the editor that opens its decks. Whenever a slide uses a pattern that `board-to-reveal/COVERAGE.md` does not list (a new kind of interactivity, animation, component, uploaded asset, layout mechanism or visualization), in the same turn:
    1. Get the repo with push access (`add_repo` with `access: "push"`), clone it, branch, and run `npm install` in `board-to-reveal/`.
    2. Extend `build.js` (and `verify.js` if the new pattern needs its own check) so it exports the new pattern faithfully. Keep `build.js` failing loudly (exit code 3, via `unsupported()`) for patterns it still cannot handle. If the new pattern changes how slides are laid out or captured (e.g. a new kind of layer), make sure the PDF download and print layout in `extras.js` still show it in its last click state.
    3. Test on the real board: Artifact `read` `project/canvas.json` and every `.dc.html` in its `order`, then `node board-to-reveal/convert.js <that project folder> <scratchpad>/out/deck.html --check`. All checks must pass (section 4, step 3) and the new slide's screenshots must match the board.
    4. **Slidewright must still work.** Add a small slide using the pattern to `board-to-reveal/test-board/` (and to `canvas.json` `order`), extend `tests/builder.cjs` to check the pattern survives a Slidewright save and still plays, and run `node tests/builder.cjs` and `node tests/run.cjs`. Also open the real deck in Slidewright (load it with `#fileDeck`, visit every slide, `__deckEditor.serialize()`, present the saved copy) and check for errors. **If the new pattern breaks Slidewright, fix Slidewright (`index.html`, `app.css` and the scripts in `js/`) in the same change.** Add any new structure Slidewright must keep to `docs/DECK-FORMAT.md`.
    5. Add the pattern to `COVERAGE.md` (and remove it from "Not supported yet"), bump `version` in `board-to-reveal/package.json`, add a changelog line, commit, push the branch, open a PR, wait for CI (it runs both test files and deploys the site only when they pass) and merge it once green.
    6. Tell the instructor in one line that the converter now handles that kind of slide, and whether Slidewright needed a change.
    Patterns already listed need no converter work, and one-off cosmetic edits never do.

## 4. Phase 2: export to reveal.js (only on request; Claude runs it)

1. **Read the latest board**: Artifact `read` with `paths` for `project/canvas.json` and every `project/*.dc.html` named in its `order` (plus each uploaded `/_blob/<id>` asset by its id). Never work from memory.
2. **Run the converter**: clone slidewright (`git clone --depth 1 https://github.com/JesseTNRoberts/slidewright`; it is public, so reading needs no extra access), run `npm install` in `board-to-reveal/`, then `node board-to-reveal/convert.js <the read's project/ folder> <scratchpad>/out/<deck-name>.html --check` (about a minute and a half). The copyright line defaults to `© <current year> Dr. Jesse Roberts`; pass `--copyright="Name"`, `--year=YYYY`, `--no-copyright` or `--no-pdf` only when the instructor asks. If the repo cannot be reached, say so. Exit code 3 names a slide pattern the converter can't handle yet: extend it per section 3, rule 11, then rerun.
3. **All checks must pass** before delivering: `total` equals the number of non-hidden boards (the build log prints `N slides (+H hidden)` and marks hidden boards `[hidden]`); Plex Sans/Mono loaded; `overflow 0`; `axe []`; `unlabeled svgs 0`; `errors []`; `requests []`; every `animated` and `build dots` entry has `bad: 0`; `extras` shows `button_on: [1]`, `button_spot: "ok"`, `copyright` equal to `total` and `copyright_not_clear: []`; `pdf` `pages` equals `total`. Look at the screenshots (tile the PNGs in `shots/` into one contact image and view it) and open any slide that looks off, including where the PDF button landed on slide 1. Fix causes on the board, or fix the converter per rule 11.
4. What the converter does (to explain or debug it): order from `canvas.json`, with boards on the `hidden` page kept as `data-visibility="hidden"` sections; runs each slide's `renderVals()` in Node (`this.props = {}`, `this.state = {step:k}`) and expands `<sc-for>`/`<sc-if>`/`{{holes}}`; removes buttons; prefixes every `id` (and `url(#…)`, `href="#…"`) per slide; `data-title` = the 48/64px title text; one `<section>` per slide preceded by `<!-- ===== Slide N: Title ===== -->`; click steps as fragments (full fade-in layers or animated movers, covered layers marked `aria-hidden`); `data-build-step`/`data-build-dot` with `buildDots()`; time-driven slides bound with `data-live`/`data-lv` and run by the slide's own component while shown; reveal config `width:1280, height:720, margin:0.03, center:false, hash:true, controls:true, progress:true, slideNumber:false, transition:'fade'`; Plex Sans 300–600 and Mono 400–500 (latin, latin-ext, greek; Mono has no greek) inlined as woff2 data URIs; reveal.js (from slidewright's `vendor/`) and, if needed, KaTeX + auto-render inlined with `</script` escaped and KaTeX SVGs marked decorative. Student extras from `extras.js`: a "Download slides as PDF" button on the title slide that builds the PDF in the browser with an inlined jsPDF (from `vendor/`; one 1280×720 page per slide, each in its last click state, no print dialog; pages are images); a copyright line (11px Plex Mono `#5A5F6B`, heard by screen readers on the title slide only) on every slide; both moved to a free spot at load; the button hidden in fullscreen and off slide 1; Ctrl/Cmd+P prints one slide-sized page per slide, last step only, with reveal's letter-paper print CSS removed. `--check` runs headless Chromium offline, screenshots every slide and click step after the fade, checks every animated element and build dot at every step, checks the extras, downloads the PDF once to `shots/deck.pdf` and counts its pages, and runs axe-core rules `image-alt`, `svg-img-alt`, `role-img-alt`, `aria-hidden-focus` with all sections visible; overflow and overlap are measured on the drawn part of anything inside a clipping container.
5. **Build the companion notebook** (required with every export). `project_read` `lecture-notebooks/STYLE.md` from the attached Project and follow it exactly. Assemble one `.ipynb` named after the deck (e.g. `<deck-name>.ipynb`) from the lecture's saved code (section 3, rule 10). If some code is from an earlier session and not on disk, recover it from that conversation's history; if nothing computed a slide number, say so in the notebook rather than writing code to match it. Rewrite the code to the style guide: one section per slide in lecture order, a few sentences on what each cell computes and why (not a repeat of the lecture), clean and documented code students can emulate, matplotlib for every figure, the standard PyTorch device pattern so it runs on a Colab T4 or a CPU, and the same seeds and constants as the slides. Build it with nbformat and execute it with nbclient (long runs: execute with `QUICK = True`, then save with `QUICK = False` and outputs cleared). Every deterministic number must match its slide; flag any mismatch in the notebook and in the reply.  A lecture with no computed content still gets a short notebook saying so, unless the instructor says to skip it.
6. **Deliver** both files with SendUserFile (`display: attach`). One line on use: arrows/Space, F fullscreen, Esc overview, S speaker notes; students use **Download slides as PDF** on the title slide (Ctrl/Cmd+P prints the same layout); `?print-pdf` shows every slide at once for checking in WAVE / Web Developer (enable "Allow access to file URLs" for local files).
   In the reply, add one line on the notebook: what it reproduces, its runtime, and any slide numbers it found wrong.
7. Later changes: edit the board, re-read it, rerun step 2, and update the notebook if a computed slide changed. Editable .pptx only when the instructor asks for PowerPoint (pptxgenjs: Calibri text, Cambria math, Consolas code, every element a real shape).

### Uploaded .pptx slides
The converter reads board slides only. If the instructor uploads a .pptx: render it to images; for slides that match board slides use the board; rebuild the rest as board artboards first (text → real HTML with nested bullets, two columns when dense; Office equations → KaTeX `\( \)` checked against the render; code → `<pre class="code">` in the code colours with indentation restored; pictures → data URIs, honouring crops, preferring the pptx's SVG; drop decorative template backgrounds; keep the instructor's wording and list suspected typos in the reply instead of fixing silently), then export.

## 5. Accessibility rules for the board (`--check` enforces them)

- Every `<img>` alt says what the figure *shows*, with the numbers printed on it, not just what it is.
- Pixel-grid images: `role="img"` plus a descriptive `aria-label` on the grid container.
- Plot SVGs (any SVG with axes or `<text>`): `role="img" focusable="false"` and an `aria-label` describing the curve (shape, key values, what is dashed for comparison; mention a step-build marker if present). The check fails if an SVG has neither a label nor `aria-hidden`.
- Decorative inline SVG (arrows, full-slide line overlays whose labels are HTML): `aria-hidden="true" focusable="false"`.
- Never carry over auto-generated pptx alt text ("Description automatically generated", web page titles); rewrite it.
- Text must fit its slide: the overflow check fails on anything past 1280×720.

### AI 4200 Week 7.2: multi-class classification, softmax, cross-entropy
- Running example: MNIST digits 0–9; logits ŷ = [−1.2, 0.3, 1.1, 0.8, −0.5, −0.9, −2.0, 4.1, 0.2, 1.6], true class 7, p̂₇ ≈ 0.81.
- Results as stated: p̂ᵢ = e^ŷᵢ / Σₖ e^ŷₖ; ∂p̂ᵢ/∂ŷⱼ = p̂ᵢ(δᵢⱼ − p̂ⱼ); ∂P̂/∂Ŷ = diag(p̂) − p̂p̂ᵀ (off-diagonal −p̂ᵢp̂ⱼ); shared sum s = Σᵢ p̂ᵢ ∂L/∂p̂ᵢ so ∂L/∂ŷⱼ = p̂ⱼ(∂L/∂p̂ⱼ − s) in O(n); H(p, p̂) = −Σₖ pₖ log p̂ₖ; with softmax folded in ∂L/∂Ŷ = P̂ − P.
- Framing: CE introduced from BCE (binary output does double duty, so BCE needs the (1−p̂)^(1−p) term; multi-class outputs have one job each). CE = negative log-probability of getting every label in the dataset right (written Pr, not P).
- Jacobian sequence: (1) backprop needs ∂P̂/∂Ŷ; (2) building it is O(n²) (sigmoid vs softmax heatmaps; MNIST 10², ImageNet 10⁶, 50k vocab 2.5 × 10⁹); (3) the product is O(n) via the shared sum, shown with the dashed common term. Lesson: off-diagonal Jacobian entries are the problem; look for shared structure.
- PyTorch: CrossEntropyLoss takes logits; `predict` returns `torch.softmax(self.forward(x), dim=1)` (full distribution, not just argmax).
- Known typos left in the instructor's own slides (ask before fixing): missing minus signs on the Derivative vs Gradient vs Jacobian slide; `super(ExampleNetwork, self):` in the dropout code; "if means" in quiz item 4.

### AI 4200: Understanding modern activation functions (Heaviside → SiLU → GLU → SwiGLU → bilinear → MoE)
- Arc: Heaviside step (zero gradient) → sigmoid (≤ 0.25 gradient, non-zero mean) → ReLU (gradient 1, mean and dying units remain; max depth pills 1 / ≈10 / ≈50 layers) → "build ReLU from H(ŷ) and ŷ" question → ReLU = ŷ · H(ŷ), a gated identity → product rule forward/backward → each gate sees only its own unit (4-unit diagram) → SiLU = ŷ · σ(ŷ) → question slide → ReLU′ vs SiLU′ with a 5-step build (ŷ = 3, 1, 0, −1, −3) → gated family (H, σ, Φ; means under N(0,1)) → GLU σ(XWᵀ) ⊙ X (4-unit diagram, each gate reads every input) → value projection σ(XWᵀ) ⊙ XVᵀ then W_out → SwiGLU → bilinear XWᵀ ⊙ XVᵀ and Shazeer 2020 results → still open → SwiGLU in a FFN, residual MLP, opened up → MoE (router gate per expert, top-k as H on experts, load-balancing loss; Kimi K2 8 of 384 experts, 1T total / 32B active).
- Instructor's vocabulary: "scaled path" (the value ŷ multiplied by the gate) vs "composed path, through the gate"; never "identity path / gate path". H(·) for the step, never max/𝟙 in derived forms. SiLU, never Swish (except to explain the SwiGLU name). "Residual MLP" means MLP blocks only, no attention.
- Colour meanings in this deck: blue = scaled path / the input ŷ, orange = gate / composed path, ink = shared gradients, gray = trunk; forward solid, gradients dashed. On the value-projection slide blue = f-dimensional, orange = n-dimensional. Product-rule factors are coloured by source: H(ŷ) and ∂H/∂ŷ orange, ŷ and ∂ŷ/∂ŷ blue.
- Diagram family: 4-input, 4-unit expanded diagrams (inputs → Σ nodes → σ(·) → × → p̂ₖ → dashed W_out fan → hₖ), with the same layer as a collapsed block underneath at the same width; MoE groups units 1–2 and 3–4 into two experts, router = a lane of Σ nodes (x W_rᵀ) → softmax → one gate per expert into an orange × after each unit; greyed experts have no lines to h.

### AI 4200: What did your MLP actually learn? (generalization, the shift test, data augmentation)
- Students' project: residual MLP on MNIST / CIFAR-10 / ImageNet, no convolutions, no extra data; augmentation allowed (it does not count as adding data). Followed by the inductive-bias / CNN lecture.
- Arc: over/underfit curves recap → model-space map (all possible models ⊃ chosen class ⊃ fits training ⊃ also fits test; 14-click runs with real fits) → deep nets cover almost everything (A/B/C prediction regions) → shuffled-label test → memorizes noise → yet works → U-curve to p = n (random-features model diagram) → double descent → not explicit regularization → minimum-norm fit (weight norm 1,041 at p = n, 2.7 at p = 10,000) → implicit regularization synthesis → rethinking generalization (7, shifted 7) → edges never trained or tested → shift poll → accuracy collapses → wrong solution → weights have addresses → pixel permutation → augmentation (shift, scale; flips rejected) → cost of augmentation → project → back to the map.
- Instructor's framing: generalization = same task, not just same distribution; augmentation changes the data (shrinks the fit set), a CNN changes the class; the training procedure (architecture, initialization, optimizer) picks among perfect fits = implicit regularization, with the optimizer-vs-architecture split flagged as debated.
